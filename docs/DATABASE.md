# Database

`prisma/schema.prisma` is the single source of truth; this document explains the *why* behind it.
Run `npx prisma studio` for a live browsable view during development.

## Tables

### `users`
Login identity for every account (staff or student). `role` is one of `SUPER_ADMIN`, `ADMIN`,
`SECURITY_OFFICER`, `STUDENT`. A `STUDENT`-role user has exactly one linked `Student` row
(`students.user_id`, unique). `email` is globally unique. `active = false` immediately blocks
login and is re-checked on every authenticated request, not just at login time.

### `students`
Profile data (`enrollment_no` unique, `department`, `course`, `year`, `semester`, ...).
Students are **never hard-deleted** — `DELETE /api/students/:id` sets `active = false` on both the
`Student` and its `User` row, preserving their full access history.

### `student_presence`
One row per student, `student_id` as primary key. This table — not any client, not the QR, not a
cached counter — is the single authoritative record of who is inside right now. `status`,
`entered_at`, `current_entry_event_id`, and `last_gate_id` are only ever written by `verifyScan()`
or `verifyExit()` inside their respective locked transactions (or by seed data for demo purposes).

### `gates`
Physical gates. `active = false` immediately blocks every device assigned to it from creating new
sessions, and blocks scans of sessions already issued for it.

### `devices`
Registered kiosks. `device_identifier` is unique and human-chosen (e.g. `KIOSK-MAIN-01`);
`device_secret_hash` is a bcrypt hash — the raw secret is generated once at registration
(`registerDevice()`) and never stored or logged in plaintext. `gate_id` is a required FK: a device
belongs to exactly one gate for its whole lifetime (re-register it under a different gate if it
physically moves).

### `security_sessions`
The dynamic, single-use **entry** QR sessions — generated by a student, verified by an officer's
device. `nonce_hash` — never the raw nonce — is what's persisted. `status` is one of
`ACTIVE → CONSUMED | EXPIRED | REVOKED` (all terminal except `ACTIVE`). `created_by_student` is
set at generation time; `gate_id`, `device_id`, and `scanned_by` are all `NULL` until an officer's
device actually verifies it — the student never chooses or knows the gate in advance.

### `exit_codes`
The permanent, reusable **exit** QR per gate — created by a security officer/admin, scanned
directly by students on their own device. Unlike `security_sessions`, there's no expiry and no
per-scan consumption: `active` is the only lifecycle flag, flipped to `false` (with `revoked_at`
set) when an officer explicitly revokes it. `getOrCreateExitCode()` is idempotent — it returns the
existing active row for a gate rather than minting a new one each time, since the same QR may be
printed and posted physically.

### `access_events`
Append-style ledger, one row per verified scan. `event_type` is `ENTRY` or `EXIT`. Exactly one of
`session_id` (set on ENTRY rows) or `exit_code_id` (set on EXIT rows) is populated — never both,
never neither; `device_id` is `NULL` on EXIT rows since no kiosk is involved in a self-service
exit. An `EXIT` row's `entry_event_id` points back at the `ENTRY` row it closes, and
`duration_seconds` is computed at write time. `session_id` is unique where set — each entry
session produces at most one event, ever; `exit_code_id` is deliberately **not** unique, since the
same exit code legitimately produces many EXIT rows over its lifetime.

### `audit_logs`
Append-only forensic trail (no route issues `UPDATE`/`DELETE` against it). `metadata` is a
free-form JSON blob for context specific to the action.

### `system_settings` / `alerts`
Key/value runtime configuration, and rule-based security alerts respectively (see
`src/server/modules/alerts/alerts.service.ts` for the trigger conditions).

## Constraints & indexes

- Unique: `users.email`, `students.enrollment_no`, `students.email`, `gates.name`,
  `devices.device_identifier`, `access_events.session_id`,
  `student_presence.current_entry_event_id`.
- Foreign keys everywhere a row references another (cascading deletes only where it's genuinely
  safe — e.g. deleting a `Gate` cascades to its `Device`s, but students are never hard-deleted so
  no student-owned row ever needs to cascade-delete).
- Indexes: `student_presence.status` (the "who's inside" query), `access_events.timestamp` /
  `(student_id, timestamp)` / `(gate_id, timestamp)` (history and analytics queries),
  `security_sessions.status` / `expires_at` (the scan/expiry lookups), `audit_logs.timestamp` /
  `(entity_type, entity_id)` / `actor_user_id`.

## Migrations

```bash
npx prisma migrate dev --name <description>   # create + apply a migration in development
npx prisma migrate deploy                     # apply pending migrations in production
npx prisma studio                             # browse data
```

The test suite uses `prisma db push --force-reset` against a **separate** database
(`TEST_DATABASE_URL`) rather than running migrations, so it always starts from an exact copy of
the current schema without needing migration history to stay in sync during rapid iteration.
